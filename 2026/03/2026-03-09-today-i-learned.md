# HikariPool 커넥션 고갈 — 범인은 코드가 아니라 DB 서버였다

> 상태: 분석 완료, 검증 진행 중

---

## 증상

Spring Boot + JPA 기반 서비스에서 간헐적으로 모든 API가 먹통이 되는 현상이 반복됐다. 특정 시간이 지나면 모든 요청이 30초씩 대기하다 실패했고, 서버를 재시작하면 잠깐 정상으로 돌아왔다가 어느 순간 또 터졌다.

특이한 점은 같은 DB를 바라보는 MyBatis 기반 서비스는 같은 시간대에 아무 문제가 없었다는 것이다. 두 서비스가 동일한 HikariPool 설정을 쓰는데, 한 쪽만 터진다.

---

## 로그에서 처음 보인 것

에러 로그를 열면 제일 먼저 보이는 건 이것이다.

```
HikariPool-1 - Connection is not available, request timed out after 30000ms
(total=10, active=10, idle=0, waiting=15)
```

커넥션 10개가 전부 active로 묶여 있고, 15개의 요청이 줄을 서고 있다. 이 에러가 일단 터지기 시작하면 거의 모든 API가 동일한 에러를 연속으로 뱉는다.

---

## 가설을 하나씩 세우고 배제했다

### 가설 1 — 트랜잭션 안에 외부 API 호출이 있는 건 아닐까

`@Transactional` 내부에서 외부 HTTP 호출이 발생하면, 커넥션을 쥔 채로 외부 응답을 기다리게 된다. DB 커넥션 고갈의 고전적인 패턴이다.

확인해보니 외부 API 연동 자체가 결제 하나뿐이었고, 장애 시간대에 결제 요청은 없었다. 배제.

### 가설 2 — OSIV가 켜져 있는 건 아닐까

OSIV(Open Session In View)가 활성화되면 HTTP 응답이 나갈 때까지 커넥션이 유지된다. 설정 파일을 확인하니 `spring.jpa.open-in-view=false`가 명시적으로 꺼져 있었다. 배제.

### 가설 3 — 트랜잭션 범위가 너무 넓은 건 아닐까

`@Transactional` 메서드 안에서 비DB 작업이 길면 커넥션을 그만큼 오래 잡게 된다. 코드를 보니 서비스 레이어에 `readOnly = true`가 전반적으로 적용돼 있었고, 데이터 변경이 있는 경우에만 별도 트랜잭션을 썼다. 코드 구조상 문제가 없었다.

여기서 한 번 막혔다. 통상적으로 의심하는 원인을 다 털었는데, 풀은 계속 고갈되고 있었다.

---

## 에러 시점보다 앞을 봐야 했다

발상을 바꿔서 에러가 터진 시점이 아니라, **그 이전 로그**를 집중적으로 뒤졌다.

타임아웃 에러가 시작되기 약 2분 전, HikariCP가 이런 경고를 남기고 있었다.

```
Connection leak detection triggered — leakDetectionThreshold 초과
```

`leakDetectionThreshold`는 커넥션이 일정 시간 이상 반납되지 않으면 HikariCP가 경고를 남기는 설정이다. 여기서 말하는 "leak"은 진짜 커넥션 누수가 아니라 **너무 오래 점유된 커넥션**에 대한 경고다.

스택 트레이스를 보면 이 경고가 반복적으로 특정 서비스 메서드 몇 개에서 발생하고 있었다. 예약 조회, 매출 합계 조회처럼 비교적 복잡한 읽기 작업들이었다.

### 커넥션을 잡고 10초 동안 아무것도 안 했다

문제가 된 요청 하나를 골라 타임라인을 재구성했다.

```
T+0.00s  인터셉터 진입, 인증 처리
T+0.40s  인증 완료 → 서비스 메서드 진입
         @Transactional 시작 → 커넥션 획득
T+0.40s ~ T+10.40s  (SQL 로그 없음)
T+10.40s Connection leak detected
```

`@Transactional`이 시작되고 커넥션을 획득했는데, **10초 동안 Hibernate SQL 로그가 한 줄도 없었다.**

Hibernate는 쿼리를 DB로 전송하기 직전에 SQL을 로깅한다. 로그가 없다는 건 쿼리를 아직 전송도 못 했거나, 전송했지만 DB에서 응답이 오지 않는다는 뜻이다. 어느 쪽이든 DB 쪽 문제다.

### 같은 시간대 다른 쿼리들도 느렸다

같은 시간대 다른 스레드의 쿼리 응답 시간을 보면 패턴이 보인다.

```
단순 COUNT 쿼리  →  약 2초
PK 단건 조회    →  약 1초
```

인덱스 문제라면 COUNT나 PK 조회가 이렇게 느릴 수 없다. DB 서버 자체가 전반적으로 느린 상태다.

하루 중 가장 첫 번째 요청으로 거슬러 올라가도 마찬가지였다. 첫 요청이 들어온 순간부터 이미 PK 조회 하나에 1초가 걸렸다. "갑자기 느려진" 게 아니라, **원래부터 느렸다.** 다만 동시 요청 수가 일정 수준을 넘으면서 비로소 풀 고갈이 드러난 것이다.

---

## 왜 JPA만 터지고 MyBatis는 괜찮았나

둘 다 HikariPool을 쓴다. 차이는 커넥션을 언제 잡고 언제 놓느냐에 있다.

**MyBatis (트랜잭션 없는 단순 조회)**

쿼리를 실행하기 직전에 커넥션을 획득하고, 쿼리가 끝나면 바로 반납한다. DB가 1초 느리면 커넥션 점유 시간도 약 1초다.

**JPA + `@Transactional`**

메서드에 진입하는 순간 `JpaTransactionManager`가 커넥션을 획득한다. 이후 쿼리 실행, 결과 수신, 객체 매핑, dirty checking까지 전부 끝나야 커넥션이 반납된다. DB가 1초 느리면 커넥션 점유 시간은 쉽게 3~10초가 된다.

`readOnly = true`를 써도 이 획득 시점은 바뀌지 않는다.

풀이 10개일 때, MyBatis는 동시 요청 10개를 버티지만 JPA는 3~4개만 겹쳐도 풀이 꽉 찰 수 있다. DB가 느릴수록 이 격차는 커진다.

---

## 진짜 원인 — InnoDB 버퍼풀이 126MB였다

DB 상태를 직접 확인했다.

```sql
SELECT Variable_name, Variable_value
FROM information_schema.GLOBAL_STATUS
WHERE Variable_name LIKE 'Innodb_buffer_pool%';
```

수치가 꽤 많이 나오는데, 하나씩 읽어보면 상태가 보인다.

### 즉시 눈에 들어온 것들 — 문제 있음

**`PAGES_FREE = 0`**

버퍼풀에 여유 페이지가 단 하나도 없다. 전체 페이지 8,064개가 전부 사용 중이다. 계산하면 `8,064 × 16KB = 약 126MB`. 서버 RAM이 4GB인데 버퍼풀에 고작 126MB만 할당된 상태였다.

**`WAIT_FREE = 9`**

빈 페이지가 없어서 InnoDB 자체가 물리적으로 멈춘 횟수다. 9번이라는 숫자가 작아 보일 수 있지만, 이게 0이어야 정상이다. DB가 응답을 멈추는 순간이 실제로 발생했다는 뜻이다.

**`LRU_FLUSHED = 27,307`**

새 데이터를 올리기 위해 기존 데이터를 디스크로 밀어내고 자리를 만든 횟수다. 2만 7천 번이 넘는다. 메모리가 부족하니 데이터가 메모리와 디스크 사이를 끊임없이 오간 것이다.

**`MADE_NOT_YOUNG = 611,860` vs `MADE_YOUNG = 65,936`**

InnoDB는 자주 쓰이는 데이터(young)와 오래된 데이터(old)를 구분해서 관리한다. 비율이 9.3:1이면 데이터가 warm 상태를 유지하지 못하고 계속 밀려난다는 의미다. 버퍼풀이 너무 작아서 벌어지는 현상이다.

**`PAGES_SPLIT = 38,776`**

B-tree 인덱스 페이지 분할 횟수가 높은 편이다. 인덱스 단편화가 진행됐을 가능성이 있다.

---

### 숫자는 괜찮지만 의미를 알아야 하는 것들

**`READS = 51,081`**

디스크에서 직접 읽은 횟수다. 높은 편이지만 이 수치만으로는 판단하기 어렵다. 중요한 건 이 값이 조회할 때마다 급격히 늘고 있느냐다. 짧은 시간 간격으로 두 번 조회해서 증가폭을 보는 게 더 정확하다.

**`READ_AHEAD_EVICTED = 617`**

InnoDB가 순차 접근을 예측해서 미리 읽어뒀는데, 실제로 쓰기 전에 버려진 페이지 수다. 버퍼풀이 좁으니 미리 읽어봤자 자리가 없어서 바로 퇴거된 것이다. 낭비된 디스크 I/O다.

**`READ_REQUESTS = 0`**

논리적 읽기 요청 횟수인데 0이 나왔다. 이건 MariaDB 버전에 따라 이 카운터가 정상적으로 집계되지 않는 경우가 있어서, 수치 자체보다는 다른 지표로 판단하는 게 낫다.

---

### 괜찮은 것들

**`READ_AHEAD_RND = 0`**

랜덤 read-ahead가 없다. 풀 테이블 스캔이 발생하지 않는다는 의미로 긍정적이다.

**`LOAD_INCOMPLETE = OFF`**

재시작 후 버퍼풀 복원이 정상적으로 완료됐다.

---

### 정리하면

버퍼풀이 126MB로 꽉 찬 상태에서 모든 쿼리가 디스크를 거쳐야 했다. `WAIT_FREE`가 이미 발생했다는 건 DB가 실제로 멈추는 순간이 있었다는 뜻이고, 그 순간에 커넥션을 쥐고 있던 트랜잭션들이 응답을 기다리며 묶이기 시작한 것이다.

### 장애가 전파된 흐름

```
버퍼풀(126MB) 포화
  → 모든 쿼리가 디스크 I/O 경유
    → 단순 조회도 1~2초 소요
      → @Transactional 커넥션 점유 시간 증가
        → leakDetectionThreshold 초과 경고
          → 동시 요청이 몰리면 풀(10개) 전부 점유
            → 신규 요청 30초 대기 후 타임아웃
```

코드는 정상이었다. DB 서버 설정이 문제였다.

## 해결

### 즉시 조치 — SET GLOBAL로 런타임 적용

서비스를 중단하지 않고 즉시 적용할 수 있는 방법을 먼저 택했다. MariaDB 10.2 이상에서는 재시작 없이 버퍼풀 크기를 변경할 수 있다.

서버 RAM 4GB, DB 전용 서버 기준으로 OS가 최소 500MB~1GB를 점유하므로 1GB를 우선 적용했다. 한 번에 2GB로 올리지 않은 건 현재 데이터 규모에서 1GB로도 충분한지 먼저 확인하기 위해서다.

```sql
-- 현재 설정 확인
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
-- 결과: 134217728 (128MB)

-- 1GB로 변경
SET GLOBAL innodb_buffer_pool_size = 1073741824;
```

적용 직후 상태:

```
RESIZE_STATUS : Completed resizing buffer pool from 134217728 to 1073741824 bytes
PAGES_TOTAL   : 8,064  →  64,512
PAGES_FREE    : 0      →  56,448  (여유 공간 87.5%)
```

변경 전 여유 페이지가 0이었던 게 56,448페이지로 늘었다. 버퍼풀의 87.5%가 비어 있는 상태다. 이제 쿼리 결과가 메모리에 올라올 공간이 생겼다.

`WAIT_FREE`, `LRU_FLUSHED` 같은 누적 수치는 이전 값이 그대로 유지된다. DB를 재시작하기 전까지 리셋되지 않으므로 이 값들은 신경 쓰지 않아도 된다.

### 영구 조치 — 설정 파일 반영

`SET GLOBAL`은 런타임에만 적용된다. DB를 재시작하면 `my.cnf` 설정값으로 돌아가므로 설정 파일에도 반영해야 한다.

```ini
[mysqld]
innodb_buffer_pool_size = 1G
```

### 이게 근본 해결인가

버퍼풀 증가는 근본 해결에 가깝다. 데이터가 메모리에서 처리될 수 있게 되면 디스크 I/O 병목 자체가 사라진다. 다만 이번에 1GB로 올린 건 현재 데이터 규모 기준의 판단이고, 데이터가 계속 쌓이면 언젠가 다시 같은 상황이 반복될 수 있다.

`PAGES_FREE`가 다시 0에 가까워지는 시점이 오면 그때 2GB로 올리거나, 상황에 따라 읽기 전용 레플리카 분리나 캐시 레이어 도입을 검토해야 한다.

### 추가로 확인할 것

`PAGES_SPLIT` 수치가 상당히 높았다. B-tree 인덱스 페이지 분할이 많이 발생했다는 의미로, 인덱스 단편화가 진행됐을 가능성이 있다. 부하가 낮은 시간대에 주요 테이블에 `OPTIMIZE TABLE`을 실행해보는 게 좋다.

## 다음에 같은 문제를 만나면

1. HikariPool 에러 로그에서 `total / active / idle / waiting` 수치 확인
2. 에러 시점보다 **2~5분 앞** 로그에서 `Connection leak detected` 여부 탐색
3. leak이 감지된 스레드의 SQL 로그 공백 여부 확인 — 공백이 있으면 DB가 응답을 안 주는 것
4. `INNODB_BUFFER_POOL_PAGES_FREE`와 `WAIT_FREE` 즉시 확인
5. `SHOW PROCESSLIST`로 현재 실행 중인 쿼리 상태 파악

### 사전에 있었으면 좋았을 모니터링

- `INNODB_BUFFER_POOL_PAGES_FREE` 임계값 알람 (예: 전체의 5% 미만)
- `INNODB_BUFFER_POOL_WAIT_FREE` 누적 증가 감지
- HikariPool active count 가 max에 근접할 때 알람
- Slow Query Log 활성화 (`long_query_time = 1`)

이 중 하나라도 있었다면 풀이 고갈되기 전에 인지할 수 있었다.
